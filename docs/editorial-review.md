# Редакционная проверка

Раздел [«На проверке»](https://rvbstr.github.io/mscmntr/?view=review) показывает опубликованный снимок `public/data/review.json` и источники с флагом `requires_identity_confirmation` из публичного каталога. Это интерфейс просмотра: решений «принять/отклонить», авторизации и назначенного редактора пока нет. Файлы изменяет владелец репозитория или редактор с доступом на запись.

## Источники-кандидаты

19 октября 2026 года владелец принял пять каналов, ранее ожидавших внешнего подтверждения: `generativegallery`, `gt_gallery`, `mmoma`, `mosmuseum`, `lumiere_gallery`. Это редакторское принятие (`editor_approved`), а не внешняя проверка. Исходные описания и доказательства сохранены. Для независимого подтверждения нужно проверить именно принадлежность канала площадке; совпадение имени и слово «официальный» в самом канале не являются внешним доказательством.

1. Откройте официальный сайт или другой ранее подтверждённый аккаунт площадки. Найдите опубликованную там ссылку на нужный Telegram-канал. Зафиксируйте URL страницы и дату проверки. Если подтверждения нет, оставьте канал кандидатом: это не повод удалять его или публиковать все найденные в нём события.
2. В `catalog/additional-sources.json`, в соответствующем элементе `sources`, добавьте внешнее доказательство в `discovery.evidence` (`page_url`, `checked_at`, `context`), обновите `discovery.identity_method`, `discovery.verified_at`, `last_checked_on` и `access_notes`. Снимите `requires_identity_confirmation` (либо задайте `false`).
3. В **том же файле**, в соответствующей связи `institution_sources`, измените `officiality` с `self_identified` на `official`, обновите `identity_evidence_url`, `identity_checked_on`, `notes`. Если это собственный канал анонсов конкретной площадки, измените `role` с `secondary_discovery` на `announcements`. Снятия одного флага недостаточно: роль `secondary_discovery` по-прежнему отправляет неоднозначно связанные события на проверку. Общие городские и межинституциональные каналы должны оставаться источниками поиска, даже если их владелец известен.
4. Обновите верхнее поле `updated_on`, сохраните правки в `main` и запустите GitHub Actions → «Проверка источников и публикация» → **Run workflow**. Рабочий процесс импортирует каталог с дополнениями, перечитает источники, сохранит результаты и опубликует сайт. Обычный push пересобирает сайт; новый сбор запускается вручную или по расписанию.

При локальной работе выполните `.venv/bin/python -m ingestion.import_catalog`, затем `.venv/bin/python -m ingestion.run --source НУЖНЫЙ_SOURCE_ID`. В коммит включите исходное дополнение, производные каталоги и изменившиеся опубликованные данные. Не редактируйте только `public/data/catalog.json`: следующий импорт перезапишет его.

Другие пометки имеют отдельный смысл: «Недоступен»/«Доступ ограничен» требуют рабочего способа доступа, а не подтверждения владельца. Для общего канала требуется связь конкретной публикации с площадкой; для многогородского — подтверждение московского или подмосковного адреса.

## Публикации на проверке

По решению владельца от 19.10.2026 включена публикация предварительных событий (`publication_policy: include_tentative`). Все пригодные для календаря кандидаты публикуются с заметной пометкой «Предварительно», конкретными причинами неопределённости и исходной ссылкой. Если год берётся из даты публикации, адрес не выделен или связь с площадкой предположительна, это записывается в `uncertainties`. Сведения не получают статус подтверждённых фактов. При экспорте в личный календарь сохраняются пометки и `STATUS:TENTATIVE`.

Для анонса только с датой завершения период показывается от даты публикации до известного завершения; карточка поясняет, что реальное открытие могло быть раньше. Дайджест с несколькими неоднозначно связанными датами публикуется одной программой с общим периодом. Извлечение без даты или без признаков события остаётся в этой очереди. Сборщик сохраняет текст поста до 16 000 символов, чтобы не терять даты в конце анонсов.

УНОВИС² (`WATCH02`) исключён из публичного каталога через `excluded_institution_ids`. Его отдельный Telegram-источник, события и очередь также исключаются при повторных сборах. Общий сайт-источник остаётся доступен другим связанным записям.

Это не список готовых событий. Здесь бывают несколько мероприятий в одном посте, новости без дат, розыгрыши и страницы с неясной связью с площадкой. Причина и извлечённый текст помогают разбору, но оригинальная ссылка остаётся основным источником фактов. Текст в JSON иногда сокращён.

1. Откройте оригинал. Проверьте точное название, площадку, адрес, дату и год, время и тип события. У выставки отделите период работы от вернисажа; у дайджеста разделите отдельные мероприятия. Дата публикации не заменяет дату начала.
2. Если событие подтверждено, добавьте запись в `manual_events` файла `editorial/overrides.json`. Обязательные поля: стабильный уникальный `event_id`, существующий `institution_id`, `title`, `event_type`, `start_date` и `primary_url`. Даты — `YYYY-MM-DD`, время — `HH:MM`, часовой пояс — Москва. Укажите известные `end_date`, `start_time`, `address` и описание. Для подмосковной площадки явно задайте `geography_scope: "moscow_region"` и `city`, чтобы событие не получило географию основного адреса институции. Если часть фактов остаётся неизвестной, не выдумывайте их.
3. Если публикация доступна редактору, но недоступна сборщику, можно явно указать `editor_verified_at` с реальным временем ручной проверки. Это подтверждение фактов редактором, а не автоматическое одобрение. Форматы и обязательные поля валидируются схемой `editorial/overrides.schema.json`.
4. Сохраните файл в `main` и запустите **Run workflow**. После завершения проверьте событие в афише и отчёт выполнения.

Пример структуры (значения необходимо заменить проверенными фактами):

```json
{
  "event_id": "EDITORIAL_STABLE_ID",
  "institution_id": "MSK068",
  "title": "Точное название из оригинала",
  "event_type": "exhibition",
  "start_date": "2026-10-17",
  "end_date": "2026-11-01",
  "primary_url": "https://example.org/event",
  "address": "Подтверждённый адрес"
}
```

Очередь формируется заново при сборе. Ручное добавление события **не снимает автоматически** все сомнения по исходному посту: один пост может содержать несколько мероприятий. Постоянных статусов «разобрано/отклонено» и истории решений пока нет. Нерелевантную публикацию не нужно добавлять в афишу; удаление строки из `review.json` не является постоянным отклонением — сборщик может вернуть её при следующей проверке. Повторяющийся ложный разбор исправляется в адаптере с примером исходной публикации.

Для уже опубликованных событий используются `corrections`, `suppress` и `duplicates` из `editorial/overrides.json`; описание есть в README. Не добавляйте ID публикации из очереди в `suppress`: это список ID опубликованных событий.

## Почему IVANY не было видно в Москве

В [оригинале IVANY](https://t.me/ivanygallery/346) указаны «ХЛЕБА», 17.10–01.11, вернисаж 17.10 в 18:00, **Балашиха, Керамическая, 1с9**. Сборщик создал отдельные записи выставки и открытия ещё 16 октября. Фильтр «Москва», включённый по умолчанию, скрывал обе региональные записи. Кроме того, 18 октября вчерашний вернисаж уже относится к архиву, а выставка продолжает идти. Используйте «Москва и Подмосковье» + «Сейчас идут» для выставки, «Архив» для прошедшего открытия.
